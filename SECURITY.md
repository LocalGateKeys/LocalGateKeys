# Security notes

## Status

LocalGateKeys is a released password manager: a Windows app (Microsoft Store and installer), an Edge extension, and an iPhone app in public beta. The source is published here so anyone can check how it protects your data. It has been through repeated internal security reviews, and the fixes are listed below. It has not yet had an independent cryptographic review, penetration test, accessibility review, or supply-chain audit. As with any password manager, keep an encrypted backup of your vault and your recovery phrase somewhere safe.

## Threat model

The app is designed to reduce these risks:

- a website obtaining credentials stored for a different web origin
- a content script directly opening the native vault without extension-background validation
- an arbitrary process connecting to the local agent without the random session token, or a native host other than the one the browser is registered to launch
- desktop fill into a changed executable binary, window title, control layout, signer, or weakly matched field
- plaintext credential persistence on disk
- accidental automatic submission
- global input capture disguised as password management

It does **not** claim to protect against:

- malware, debuggers, screen readers, injected code, or an administrator already controlling the user's desktop session
- a compromised browser, browser extension platform, Python runtime, dependency, or operating system
- a malicious page seeing credentials that the user intentionally fills into that page
- physical access while the vault is unlocked
- phishing on a correctly matched desktop executable that renders attacker-controlled content
- loss of the only vault file together with a forgotten master password and no recovery phrase
- rollback by an attacker who can also delete or forge the adjacent local generation anchor

The vault detects older generations while its local generation anchor remains
intact. The anchor is authenticated with a key derived from the vault's data key,
so it cannot be rewritten without unlocking the vault (the optional DPAPI seal on
Windows adds no protection beyond that MAC, because a missing seal is accepted), but it is still a local file: deleting it
together with the vault file is not detected. It is not an external,
tamper-proof rollback authority.

## Prohibited capture techniques

This project intentionally contains no:

- low-level/global keyboard hooks
- raw-input recording
- clipboard monitoring
- screen/OCR credential extraction
- process-memory scanning
- browser-profile database decryption
- DLL injection or game-process instrumentation
- sign-in submission without explicit opt-in and destination checks

A feature request that requires any of those mechanisms should be treated as a new security review, not a normal compatibility patch.

## Browser boundary

The extension uses Manifest V3 (Chromium service worker; Firefox variant generated by `browser-extension/build-firefox-manifest.cjs`) and separates untrusted content-script data from privileged Native Messaging access.

- **Static host access is deliberate.** `host_permissions` covers `http://*/*` and `https://*/*` and the content script is declared statically. The save-prompt flow needs the script to be present *before* the user submits a login form, without any click on the extension, so `optional_host_permissions` + `activeTab` cannot replace it: `activeTab` is only granted after an extension gesture, which is after the submit it would need to observe. `activeTab` is still requested so that the popup's manual Fill works on Firefox, where MV3 host permissions are optional until the user grants them. The popup never requests new permissions at runtime.
- Save prompts are on by default per origin and can be turned off per exact origin from the popup ("Turn off save prompts on this site"); the list lives in extension storage and never leaves the browser.
- `content_security_policy.extension_pages` is `script-src 'self'; object-src 'self'`: no inline or remote script can run in the popup.
- **Frames.** The content script runs in all frames but disables itself unless every ancestor shares the document's origin. The service worker does not trust that: for each request it walks the browser-reported frame tree (`webNavigation.getFrame`, `parentFrameId`) from the sender frame to frame 0 and requires every hop to have the same canonical origin as `sender.url`. Cross-origin iframes, and same-origin frames nested under a cross-origin parent, are refused before any native call. Nudges are addressed to the exact `frameId` that navigated.
- **Document pinning.** On Chromium the request is bound to `sender.documentId` and `documentLifecycle === "active"`. Firefox exposes neither; there the check falls back to the tab id plus the frame's current URL origin, and the native context key uses `frame:<id>` so two frames of one tab never share a context. A `documentId` present on one side only is treated as a mismatch.
- The service worker derives the authoritative origin from `sender.url` and compares it with the request; page-supplied origins, tab ids, frame ids and document ids are never used.
- Public HTTP origins are rejected; HTTP is accepted only on loopback for the included demo.
- Shadow DOM: field discovery walks *open* shadow roots only; closed roots (including the extension's own UI) are unreachable. Hit-testing descends through open hosts so a page overlay still blocks filling; `safeForm` (same-origin `action`/`formaction`, `_self` target) applies unchanged to forms inside shadow trees.
- **Form destination.** `safeForm` resolves `action` / `formaction` the way the browser does (against `document.baseURI`, so an injected `<base href>` is honoured), refuses a page whose `<base href>` is cross-origin or whose `<base target>` is not `_self`, and refuses the whole form if *any* submitter (buttons, `input type=submit|image`, including ones attached with `form=`) has a cross-origin `formaction` or a non-`_self` `formtarget`. Form properties are read through prototype accessors so controls named `action` or `elements` cannot shadow them.
- **In-page UI tampering.** The field icon and panel hosts are pinned with `!important` inline styles and, where supported, promoted to the top layer (`popover="manual"`). Every click must be trusted and is refused unless the host is still a direct child of `<html>`, its computed style is untouched (opacity 1, visible, no transform / filter / clip-path / mask / blend), its geometry matches what was placed, `elementFromPoint` at the click resolves to the host, and no page popover, modal dialog or fullscreen element overlaps it. A single matching account still opens the picker, so filling always takes two deliberate clicks. Residual risk: on browsers without popover support (Chromium < 114), a `pointer-events:none` page element stacked above the icon is invisible to `elementFromPoint`.
- **DOM clobbering.** The content script's re-injection guard is a `Symbol.for` key, and the `browser`, `LGKHeuristics` and `LGKLoginSafety` globals are accepted only after a function-shape check; `LGKHeuristics` is a non-writable, non-configurable property. A page element with a matching `id` cannot disable or replace them.
- Page heuristics (sign-in / logout / failure labels, `heuristics.js`) are localized but conservative: exact label equality for the single-button sign-in rule, Unicode word-boundary matches otherwise. Automatic submit still requires exactly one visible POST submit button with an exact sign-in label; there is no Enter injection or `form.submit()`.
- Website icons are off by default, on the desktop and the iPhone (Settings › "Show website icons"), and on the desktop strict offline mode blocks them. Only the site's own address is requested (`https://<host>/…`); no username, password or vault data is sent, but each download tells that site, and anyone watching the network, that this vault holds an account there. Downloads are public HTTPS only (no private, local, site-local, multicast or embedded-IPv4 addresses; the iPhone resolves the name first), size- and time-limited, and the image is decoded within fixed limits and re-encoded. The desktop keeps icons in memory and clears them on lock; the iPhone caches them in its app container and fetches only while unlocked.
- Site icons come from the browser's favicon cache on Chromium (`favicon` permission, no network request). Firefox has no such API; the Firefox manifest drops the permission and saved entries use the neutral icon.
- The extension declares no `web_accessible_resources`: in-page icons are inline SVG built inside closed shadow roots, so a page cannot detect the extension by probing `chrome-extension://` URLs. The Firefox manifest builder deletes the key as well.
- Released values (passwords, usernames, TOTP codes, card and identity fields) are blanked in the content script on every path, including early returns when the page changes during a native call. `visible()` treats opacity below 0.1, collapsing `clip-path` / `clip`, and zero-size clipping ancestors as hidden.
- The native-host manifest pins the fixed Chromium extension ID; the Firefox id is `localgatekeys@localgatekeys.app` (`browser_specific_settings.gecko`) and must be added to the host's `allowed_extensions` before Firefox can connect.
- The native host also checks the browser-supplied caller origin and fails closed when launched without it.
- The desktop agent gives a second save confirmation displaying the canonical origin and username.
- Fill responses contain one selected credential, never the whole vault.
- **Site matching.** Internationalised host names are converted with UTS-46 non-transitional processing (the `idna` package), the same mapping browsers use, so `straße.de` is stored as `xn--strae-oqa.de` rather than collapsing to `strasse.de`. Origins saved before this change are plain ASCII and are not recanonicalised; an old row keeps matching only the host it literally records, which fails closed. `base_domain` rows use the bundled Public Suffix List snapshot (`localvault/assets/public_suffix_list.dat`, ICANN and PRIVATE sections, wildcard and exception rules, plus one local narrowing rule `*.web.core.windows.net`), so a login is never offered to another tenant of a shared hosting suffix. If the list is missing or truncated, every host is its own base domain. `starts_with` URL rows narrow which entries are *offered*, but they are not an isolation boundary: any page on the same origin can change its path.
- **Save prompts.** Browser save prompts never reveal whether a captured password matches the saved one. For a submitted login the desktop app tells the extension only whether an account with that username is already saved for the origin (`new` or `exists`, the same model as Safari), and the page sees the same prompt either way. The password is compared only inside the desktop app after the user clicks Save or Update. If it is unchanged, the app says "Already saved" in its own window and writes nothing. The extension's `session_id` is compared with the session token in constant time; identity and card approvals require it, and a `session_id` sent with a manual save, even an empty one, must match the current session.
- **Probe limits.** `check_browser` / `capture_browser` (used to decide whether to offer a save prompt) still reveal whether a username is saved for the origin, so they remain rate-limited. On the desktop, while the vault is unlocked, they answer at most 10 checks per origin, 15 per site (registrable domain) and 60 in total per 60 s; past the total each site keeps 3, up to a hard cap of 240. Safari on iPhone allows 10 per origin and 30 in total per 60 s.
- **Save prompt after a redirect.** A captured login waits in memory for its tab (90 s, on the desktop and in Safari on iPhone). The next document on the same origin may show it. For 12 s after the capture, a document in the same tab on another origin of the same site may also show it: same scheme and port, and the same registrable domain by the bundled Public Suffix List (`login.paddle.com` → `vendors.paddle.com`). Never across a public suffix such as `github.io`, never for IP addresses, never in another tab. The login is saved for the origin it was typed on, and the panel and the desktop confirmation name that origin. Filling stays exact-origin.
- **Page URL.** For multi-URL logins the content script sends `location.href` (fragment stripped, never credentials) next to `origin` in `begin_browser` / `get_browser`. The service worker re-derives the sender origin from `sender.url`, forwards the `url` only when its canonical origin is identical, and otherwise drops it so the broker matches the origin alone; the broker independently fails closed (`invalid_request`) on a mismatched `url`. Choices carry the broker's `match` kind and the in-page picker labels anything wider than `exact_origin`.
- **Card fill** (`card_protocol: 1`) mirrors identity fill: `begin_card_browser` returns metadata only (title, brand, last four, which tokens exist), never a number or CVV. The user ticks fields in the extension's closed-shadow-root panel, defaulting to the tokens present on the page with the security code **unticked**; the desktop app then shows the trusted native review (number as `•••• 1111`, CVV masked) and the single-use approval is bound to the lease, origin, tab/document context, item revision and the selected tokens. `release_card_browser` is gesture-gated like `get_browser`; the page fills only the approved tokens into controls that pass the same `safeForm` / `onTop` checks as logins, never submits, discards a reply that carries any unapproved token, and blanks every released value from memory immediately after the fill. Payment forms are recognised from `autocomplete="cc-*"`; name/id heuristics cover only number, expiry and CVV and only inside a scope that already contains a card-number-like field. The PIN has no token and is never released.

- **Passkeys** (`passkey_protocol: 1`, Chromium only). `webauthn-page.js` runs in the page's own JavaScript world (`"world": "MAIN"`, `document_start`) and wraps `navigator.credentials.create` / `.get` for `publicKey` requests. It holds no secrets and makes no trust decisions: the page can see, call, replace or forge it and its `postMessage` channel, which grants nothing it could not do by calling `navigator.credentials` directly. The channel carries only the page's own request and the credential meant for that page. `webauthn-bridge.js` (isolated world) relays same-window, tagged messages to the service worker. The service worker applies the same sender-derived origin, `documentId` and same-origin frame-ancestry checks as fill, and requires the active tab. Cross-origin iframes therefore get the browser's own authenticator. The agent (`passkeys.py`, `passkey_broker.py`) builds `clientDataJSON` itself from that origin, so the signed origin is never page-chosen. It accepts an rpId only when it equals the host or is a registrable suffix of it (never a public suffix; Public Suffix List), rejects IP origins and allows HTTP only on `localhost`. Every create, and every get that has a stored candidate, shows a desktop dialog naming the site, page and profile. Unless the site asks for `userVerification: "discouraged"`, it then verifies the user with Windows Hello or the master password (the UV flag reports which). A get with no matching passkey falls back to the browser with no dialog. After any prompt that ends without a credential (Cancel, "Use browser or another device", a cancelled unlock, an existing passkey, failed verification), the same origin falls back silently for 10 s, so a page that forges requests through the MAIN-world channel can raise at most one LocalGateKeys prompt per 10 s. Page-supplied site and account names are flattened to one line with control and bidi characters removed before they reach the dialog. Focus returns to the previously active window when a prompt closes, because the browser rejects WebAuthn calls from an unfocused page. An approval that arrives more than 80 s after the request is discarded, so no passkey is stored after the extension has given up. Keys are ES256 (P-256) PKCS#8 inside the encrypted vault item and never leave the agent; replies carry signatures only. The signature counter is always 0, with the backup-eligible and backed-up flags set (synced-style passkeys), so signing in never rewrites the vault item. Attestation is `none`. Every other failure (app not running, vault locked and unlock cancelled, older bridge, malformed options) hands the original options to the browser's own authenticator. A create the page aborts after approval can still leave a passkey the site never received; the user can delete it in the app. The wrapper is detectable by a page (its function source differs from the native one), unlike the rest of the extension.

A web page can imitate an in-page LocalGateKeys banner. The native desktop confirmation is therefore the authoritative save UI. A production build should move more confirmation UI into trusted browser chrome.

## Desktop boundary

The desktop path reads accessibility metadata only:

- foreground window handle, title, process ID, and executable path
- Authenticode metadata when available
- editable control name, automation ID, class/framework, geometry, visibility, enabled state, and `IsPassword`

It never requests an existing password value.
For a control marked `IsPassword`, the app also discards its accessibility `Name` before
displaying or storing the selector, in case a defective provider leaks sensitive text there.

Before fill, the app checks:

1. exact normalized executable path
2. exact executable SHA-256 fingerprint
3. exact complete edit-control layout fingerprint (a change asks for confirmation, see below)
4. exact normalized saved window title (a change asks for confirmation, see below)
5. saved Authenticode signer certificate thumbprint when one was available during binding
6. a strong, unambiguous UI-control selector
7. a protected password-field type when the app originally exposed one

Discord is an explicit compatibility exception because its updater recreates
the executable under a new versioned `app-*` directory and its embedded login
controls are recreated between launches. Discord bindings require a versioned
`%LOCALAPPDATA%\Discord\app-<version>\Discord.exe` path and a freshly verified,
valid Authenticode signer with subject `Discord Inc.`. They resolve exactly one
current protected password field (plus an unambiguous username field when one
was saved). This compatibility policy permits updates without pinning the old
binary hash, version directory, title, or complete control layout. Other desktop
applications retain the strict checks above. When an identical (or same-signer)
binary shows a changed window title or edit-control layout, the app asks before
filling or adopting it.

If the app exposed an unprotected field and the user explicitly saved that mapping, LocalVault requires a stronger selector score and displays a fresh confirmation before every fill.

The fallback input path sends outbound Unicode keystrokes only after focus is moved to the selected control. It does not install a hook and does not observe inbound keys. Some apps, elevated windows, anti-cheat systems, or custom renderers will reject this operation; that is an expected safe failure.

## Vault cryptography

Current format version: `3`. Versions `1` and `2` remain readable and are promoted
to `3` at the first master-password unlock (v2) or by the guarded catalog migration
(v1). Every promotion runs under a crash-safe migration journal with a verified,
encrypted pre-migration backup; an interrupted promotion is rolled back before the
next unlock.

**Key hierarchy (v3).**

- A random 256-bit data key (DK) encrypts the catalog with AES-256-GCM using 12
  fresh random nonce bytes per save. The associated data authenticates the public
  header identity: format version and identifier, catalog identifier and version,
  `vault_id`, key generation, write generation and cipher name.
- DK is stored only wrapped. Each wrapper is `AES-256-GCM(DK)` under its own random
  nonce; its associated data binds the same header identity plus the wrapper name
  and the wrapper's public metadata (for the password wrapper, the complete Argon2id
  parameter block and salt). A swapped KDF block or a wrapper copied from another
  vault fails authentication before any key is used.
- Password wrapper: KEK = Argon2id(master password). Changing the master password
  rotates DK (see `rotate_data_key()` below) and wraps the new DK under a fresh
  salt and KEK, so an old password plus an old vault copy or backup cannot open the
  current vault. Rolling backups written under the old key are purged and one fresh
  backup is written under the new key. The recovery wrapper is re-created when the
  phrase is supplied; otherwise it is invalidated and the user is asked to create a
  new phrase. Older copies still expose their own (pre-change) contents to someone
  who knows the old password. Recovery-phrase unlock followed by a new master
  password (`set_master_password_after_recovery`) rotates DK the same way; the
  phrase that opened the session is re-wrapped under the new DK and keeps working,
  and Windows Hello and camera bindings are revoked.
- Recovery wrapper (optional): a 24-word BIP39 English phrase (256 bits of entropy
  plus an 8-bit checksum; the bundled word list is verified by SHA-256 when loaded)
  is expanded with HKDF-SHA256 and a per-wrapper random 16-byte salt into a
  recovery key that wraps DK. Regenerating or removing an existing phrase rotates
  DK (new key, rolling `vault-*.json` copies purged, Windows Hello must be set up
  again), so the previous phrase cannot open the current vault or any copy written
  after the change; older `before-restore-*`/`migration-*` copies and external
  backups made before the change still accept the old phrase, and the app says so. The phrase is shown once, must be retyped in part
  before the card closes, and is never stored by the application; backups and
  recovery kits only record that a phrase exists.
- Windows Hello and camera sidecars wrap DK, never the master password. v2-era
  sidecars wrapped the Argon2id output, which v3 inherits as DK at promotion, so
  they are converted by rewriting their vault context; a sidecar that cannot be
  converted is revoked inside the authenticated payload and reported for
  re-enrolment instead of being trusted.
- The camera sidecar is sealed with current-user DPAPI, so while camera unlock is
  on, an attacker with a copy of the disk and the Windows account password can
  unwrap DK without the master password; the consent text says so. Turning camera
  unlock off needs the master password, deletes the sidecar and rotates DK, so any
  earlier copy of the sidecar wraps a retired key. If a recovery phrase exists, the
  rotation replaces it: the old phrase stops opening the vault and the new one is
  shown once and must be confirmed. A profile whose camera sidecar exists cannot
  be deleted until camera verification is removed this way.
- Decrypted catalog JSON and attachment plaintext are built in `bytearray` buffers
  and zeroed after use (AES-GCM `decrypt_into`); individual field strings remain
  ordinary Python strings and are not wiped.
- `rotate_data_key()` generates a fresh DK, re-encrypts the catalog, increments
  `key_generation`, re-wraps the password wrapper (and the recovery wrapper when the
  phrase is supplied; otherwise it is invalidated and reported), revokes biometric
  grants and purges rolling backups written under the previous key.

Parameters:

- KDF: Argon2id; default 64 MiB memory, 3 iterations, parallelism 4, 32-byte output
- salt: 16 random bytes per wrapper
- encryption: AES-256-GCM, 12 fresh random nonce bytes per sealed object
- write behavior: temporary file, flush + `fsync`, atomic replace

The parser bounds the file size (24 MiB), the header shape, the number and field
sizes of wrappers, the catalog version and the KDF parameters (8-512 MiB, 1-10
iterations, parallelism 1-16) before any derivation runs. Unknown future format
versions are rejected rather than guessed at.

The Argon2 setting follows RFC 9106's memory-constrained profile and should still be benchmarked on supported hardware.

**Rollback anchor.** Each save records the committed write generation in
`<profile>.generation.json`, authenticated with HMAC-SHA256 under a key derived
with HKDF-SHA256 from DK (`localgatekeys|rollback-anchor|v1`) and bound to the
`vault_id`. On Windows the MAC is additionally sealed with current-user DPAPI when
`win32crypt` is importable; otherwise the anchor is HMAC-only and a warning is
logged once. The seal is not required on read, so the HMAC is the actual barrier. A plaintext (v1) anchor next to a v3 vault is rejected, and v3 saves
record `rollback_anchor_required` inside the encrypted payload; when the anchor is
missing the unlock still succeeds (backup verification and restores copy a vault
without its anchor), but the app warns that rollback protection was reset and a
new anchor is written. An anchor that fails authentication blocks the unlock. A
migration journal found on disk never restores its saved anchor and is discarded
if its source generation is older than the current anchor. The
anchor is never reset to zero: the compatibility restore API leaves it untouched
(an older restored copy therefore fails the rollback check at the next unlock),
and the verified restore raises `RollbackRequiresConfirmation` when the backup is
older than the anchor or the anchor belongs to a different key lineage. Only an
explicit confirmation replaces the anchor with the restored generation.

**Unlock throttling.** Wrong master-password attempts (vault unlock,
recovery-phrase unlock and in-session reauthentication) are counted per profile
in `<profile>.unlock-throttle.json`, HMAC-SHA256-protected with a per-profile
random key that is DPAPI-sealed on Windows when available. The first five
attempts are free; afterwards the wait doubles from 2 s up to a 60 s cap, measured
with a monotonic clock, and a success resets the counter. An unreadable or forged
counter fails closed to the maximum wait, and restarting the application re-arms
the persisted wait instead of shortening it. The unlock dialog shows the countdown
and keeps the Unlock button disabled until it expires. Each save records the
throttle key's id and the vault's location in the v3 header, inside the catalog's
associated data. At that location a missing, replaced or downgraded throttle key
fails closed to the maximum wait (never a lock-out). A copy at another path (a
restore, a verified backup) is not bound, and a vault last saved by an older
release is bound at its next save. Residual risk: restoring an older counter file
that is correctly MAC'd under the same key restores its lower count; this needs
same-user write access. Vaults saved by this release cannot be opened by older
releases.

## Backup, transfer, attachment and sync cryptography

All derived formats reuse AES-256-GCM with 12 fresh random bytes per sealed object and fail closed on any header or authentication mismatch.

- Vault-only backups (`.lgk`, envelope v2) and full profile backups (v2 container) derive their key with Argon2id using the vault defaults for new writes (64 MiB memory, 3 iterations, parallelism 4, 32-byte output). The parameters are stored in the header and are part of the associated data. Readers accept any header inside the vault's bounded range (8-512 MiB, 1-10 iterations, parallelism 1-16) and reject anything outside it before derivation runs; v1 `.lgk` envelopes (constant associated data) and older 32 MiB files remain restorable.
- Selective transfer packages use the same Argon2id defaults, bounds, and header-in-associated-data rule.
- Attachment sidecars (v2) carry only identity in the plaintext header (format, version, attachment id, store id). The plaintext size, SHA-256 digest, and per-attachment key live in the encrypted catalog record; integrity is verified after decryption against that record. v1 sidecars, whose header also exposed size and digest, remain readable.
- LAN sync typed items (v2) are sealed under a pairwise channel key derived with HKDF-SHA256 from the static X25519 shared secret of the two paired devices (salt: sync group id; info: protocol label, both device ids, both exchange public keys). Each record uses a random 96-bit nonce and binds the item id, item revision, sender device id, and protocol counter in the associated data; the receiver re-derives those values from the authenticated envelope and rejects mismatches, records from a sender other than the authenticated peer, and retired v1 records. The channel derivation is static-static because records are sealed before a transport session exists and may be retried across sessions.
- **LAN session (protocol v2).** Every connection carries those records inside a transport session whose key is derived with HKDF-SHA256 from a fresh per-connection ephemeral X25519 exchange mixed with the static-static exchange of the paired devices (salted with the signed hellos, info bound to the session id). Each ephemeral private key is used once and erased, so a later leak of a device's exchange key does not open recorded traffic (forward secrecy). There is no downgrade: a hello of another version is refused, and an older device must be updated before it can sync over Wi-Fi.
- **Pairing.** After a QR or copied-code request, both devices show the same 6-digit verification code and the inviting device asks Accept / Decline; nothing is sent and nobody is added before Accept, and no answer within 60 s declines. Undo still removes a device that was accepted by mistake.
- **Signing keys.** Key file format 2 lists each member's view-signing key with a proof signed by that key, both covered by the key file MAC. Folder sync checks a view's signature against the key in the accepted key file first, else the device's LAN-paired key, else the key pinned on first use; only the key file can change a pinned key, and a change is reported.
- **LAN listener.** Before a verified hello it holds at most 1 connection per source address and 3 per /24 (IPv4) or /64 (IPv6) network, and keeps one slot for peers that completed a verified hello in the last 15 minutes (at most 4 connections, 2 per address).

Known limitations of sync:

- **First-use pins for older members.** Members of a format-1 key file (written by older apps) have no signing key in it, so their views are still checked against the first key seen signing for that device. A holder of the group key who writes a signed view for such a device before it does gets their key pinned, and the device's real views are refused as forged until it leaves and joins again with a current app.
- **The Accept code checks the device, not the person.** Anyone who saw the QR code or copied text can try to pair while it is shown; the user must compare the code on both screens.
- **Hello replay window after restart.** The last hello counter received from each LAN peer is kept in memory only and starts again when the app restarts, so a recorded hello is not rejected as a replay after a restart; the session key still needs a paired device's private exchange key.
- **Firewall scope from source.** The Windows Firewall rule for LAN sync names the executable that listens. Packaged builds scope it to the app executable; a source checkout scopes it to the whole `python.exe` interpreter, so any script run by that interpreter is allowed too.

## Memory handling

The data key and every key-encryption key live in `bytearray` buffers:

- `VaultSession.lock()` overwrites the DK buffer and drops the decrypted payload.
- KEKs, recovery keys, rollback-anchor keys and throttle keys are zeroed in
  `finally` blocks as soon as the wrap, unwrap or MAC that needed them completes;
  a failed unlock zeroes the candidate key before the error is raised.
- A master-password change or data-key rotation replaces the DK buffer and scrubs
  the previous one.
- The immutable `bytes` copies that the AES-GCM, HKDF and HMAC primitives require
  are created immediately before the call inside `try`/`finally` and deleted
  afterwards. No session attribute keeps a `bytes` copy of the key; tests assert
  this and that the buffer is zero after `lock()`.
- The master password becomes a wipeable `SecretText` buffer at the WebView
  bridge or, for re-authentication prompts, in the UI port. Argon2id runs
  directly on that buffer, so no Python `str` or `bytes` copy is made for key
  derivation. The buffer is wiped when the operation that took it ends,
  including on errors.

Residual exposure that this does not remove:

- `del` on an immutable `bytes` object only drops a reference; the allocator
  decides when the memory is reused, and the `cryptography`/Argon2 native layers
  and `hmac` take their own transient copies that Python cannot scrub.
- a displayed recovery phrase is a Python string, which is immutable and may
  have copies.
- the master password is wiped on the app's side (see above), but the WebView2
  page keeps its own copy of what was typed, and the bridge's JSON-decoded
  `str` of it lives for the duration of the call; the app cannot erase either.
- the KDBX export password is handed to the KDBX writer library as a Python
  `str`, which cannot be zeroed.
- garbage collection timing is not deterministic.
- the interpreter, crash dumps, paging, or security tools may retain memory.

Production key handling should move into a small native component using locked memory and explicit zeroization, with crash-dump policy and OS-backed sealing.

## Native bridge

On Windows, the browser native host connects through a current-user named pipe
with a restricted DACL and remote clients rejected. Requests use a random
per-agent token, length-prefixed JSON (1 MiB frames, strict UTF-8/JSON object
parsing, fuzz-tested), and size limits.

**Agent token.** `agent-state.json` stores the token DPAPI-protected (user scope,
fixed application entropy, no UI prompt, `protection: "dpapi-user"`) behind an
owner-only, non-inherited file DACL. The native host unprotects it in memory and
sends it on every frame. If pywin32 is missing the token falls back to plaintext
(`protection: "none"`) and the diagnostics report warns `agent_token_unprotected`.

**Install pin.** The agent trusts only the executable the browser is registered to
launch: it reads this user's HKCU `NativeMessagingHosts` registrations (Chrome, Edge,
Firefox), requires them to agree, and requires the connecting process to run exactly
that file. Frozen builds additionally require the host to live in the app's install
directory and, when the agent is Authenticode-signed, to carry the same signer
thumbprint.

**Browser ancestry.** Knowing the registered host path is not enough: any
same-user process could start that host and write frames to its stdin. The host
therefore walks its own parent chain at start-up (`browser_ancestry.py`: Toolhelp32
parent PIDs, `QueryFullProcessImageNameW`, `GetProcessTimes`, `WinVerifyTrust`
without network revocation lookups), and the agent repeats the walk for the
connecting host. After skipping the host's own launcher images, the chain may pass
through at most one `cmd.exe` from the system directory (Chromium browsers launch
hosts through `cmd /d /s /c`) and must then reach an allow-listed browser signed by
its vendor: chrome.exe (Google LLC), msedge.exe (Microsoft Corporation), brave.exe
(Brave Software, Inc.), firefox.exe (Mozilla Corporation), vivaldi.exe (Vivaldi
Technologies AS) or opera.exe (Opera Norway AS). Every parent must have been
created before its child, which defeats PID reuse. A host that fails the check may
only `ping` (used by the app's own Connections test); every other request gets
`caller_not_browser`. This raises the bar for a same-user process but is not a
boundary against one: it can still spoof the parent-process attribute or drive a
real browser. `install.json` (user-writable) is only a cross-check that can veto, never
redirect trust. Failures are fail-closed with fixed codes (`client_pin_unregistered`,
`client_pin_mismatch`, `client_signer_mismatch`) and appear in the Connections
diagnostics. The host, in turn, checks the server process ID and user SID before
sending the token.

**User gesture.** The extension's `user_gesture: true` is a client assertion the
agent cannot verify. Fill, 2FA and save requests now carry a broker-issued
`gesture_nonce` (16 random bytes, 30 s, single use, bound to origin and tab
context) minted by `begin_browser`, `begin_totp_browser` or
`begin_gesture_browser`, so a stale or replayed request cannot reuse an earlier
gesture. Because only a host launched by a real browser can reach these actions
(see Browser ancestry), the boolean cannot be sent by an arbitrary local process.
The legacy boolean is honoured only while `legacy_gesture_compat` is on
(off by default since settings v8; when on, recorded as a diagnostics warning) and `ping` no longer reveals the
session lease or profile.

The native host opens the pipe with `SECURITY_SQOS_PRESENT |
SECURITY_IDENTIFICATION`, so a squatting server cannot impersonate it.

The non-Windows loopback TCP transport is a development fallback: it is refused
unless `LOCALGATEKEYS_ALLOW_TCP_FALLBACK=1` is set, binds and connects to
127.0.0.1 only, and carries the token on every frame.

These are defense-in-depth controls, not a same-user malware boundary. A
malicious process running as the same user may inspect state or process memory.

## Helper processes, imports and unlock policy

- **Plaintext exports** are written into a private `.lgk-export-*` folder whose
  owner-only ACL is applied before the file exists; the empty file is restricted
  again before the first byte, then atomically moved into place. KDBX export
  passwords need at least 12 characters, like every other password in the app.
- **Full-backup restore over an existing vault** requires that vault's password,
  refuses an older or foreign backup without explicit confirmation, and turns off
  autostart, automatic sign-in, per-entry sign-in, desktop-fill approvals and
  Hello/camera bindings in the restored profile.
  A selected backup is copied into a new owner-only scratch folder before its hash
  is checked and it is opened, never as a bare file in %TEMP%.
- Backup verification works in a private temporary folder and never upgrades an
  older envelope, so it leaves no migration copy behind.
- **Data folder ACL.** The main app gives the data folder a protected owner-only
  DACL (current user and SYSTEM, inherited by everything inside) once at startup,
  and skips it when the folder already has that DACL. The native host and pipe
  helpers never rewrite it. A `LOCALGATEKEYS_DATA_DIR` folder gets this ACL only
  if LocalGateKeys created it (marker file `.localgatekeys-owned`); an existing
  folder named there keeps its own ACL.
- **Popup fallback.** If the popup's navigation lock cannot be installed, the
  popup is disabled and its prompts are shown in the main window.
- **Packaging.** The installer installs only into
  `%LOCALAPPDATA%\Programs\LocalGateKeys` and refuses any other folder, including
  one given with `/DIR=`. Both executables restrict DLL search
  (`SetDefaultDllDirectories`) and refuse images from remote shares or with a
  low integrity label. The native-host log rotates at 1 MiB (about 2 MiB on disk).
  The build refuses output folders that other accounts can write. Released
  binaries are not yet Authenticode-signed.

- **No search-path executables.** Every helper the app starts runs by absolute
  path under `%SystemRoot%\System32` (`winpaths.system32()`): Authenticode checks
  use `WindowsPowerShell\v1.0\powershell.exe` with `PSModulePath` limited to the
  in-box modules and the module-qualified
  `Microsoft.PowerShell.Security\Get-AuthenticodeSignature`; ACL changes use
  `icacls.exe` and grant by the process token's SID, never by a user name from the
  environment. The OCR runner refuses a non-absolute executable. A binary planted
  in the application or current directory therefore cannot impersonate a helper or
  forge a signer. Helpers run with `CREATE_NO_WINDOW`.
- **Imports.** KDBX database and key-file XML is parsed with expat handlers that
  reject any DOCTYPE, entity, unparsed-entity or notation declaration regardless of
  encoding (a UTF-16 file cannot skip the check). Deeply nested JSON, encrypted or
  unsupported-compression 1PUX members and other decoder errors surface as the
  importer's format error. Import KDF work is capped (KDBX Argon2 at 32 GiB of
  memory x iterations, AES-KDF 50 M rounds; Bitwarden at its own limits: PBKDF2 2 M
  iterations, Argon2id 10 iterations, 1 GiB, 16 lanes). Importers stop as soon as
  they have seen more than 5,000 items, decompressed JSON is capped at 16 MiB, KDBX
  entries are counted in the expat pre-pass, protected KDBX values are size-limited
  before decryption, and diagnostics are capped, so a small crafted file cannot
  exhaust memory or stall the app.
- **Emergency lock.** "Master password required" survives exit and relaunch: the
  emergency lock writes a per-profile marker under `unlock-policy/`, Windows Hello
  and camera unlock are not offered while it exists (any contents, or an unreadable
  file, count as present), and only a master-password or recovery-phrase unlock
  removes it. Deleting it requires same-user write access, which is outside the
  threat model above.
- **Settings and logs.** A non-numeric timeout (including JSON `false`) falls back
  to the default instead of disabling auto-lock. The error log redacts values of
  secret-named assignments (`password=`, `token:`, `Authorization: Bearer ...`)
  of any length, in addition to long opaque runs.
- **PDF preview.** The active-content check decodes `#xx` name escapes and matches
  whole names (`/JavaScript`, `/JS`, `/OpenAction`, `/AA`, `/Launch`,
  `/EmbeddedFile(s)`, `/RichMedia`, `/SubmitForm`, `/GoToR`, `/GoToE`,
  `/ImportData`). Names inside compressed object streams are not inspected.
- **Licence server.** A checkout claim is bound to an order atomically in D1, so
  of two orders racing for one claim the first wins; the other order's licence
  stays under its own token and `/recover` finds it. `/recover` allows 5 attempts
  per email per hour, in addition to the per-IP rate limit.

Known limitations:

- **CSV export.** Values beginning with `=`, `+`, `-` or `@` are written as is, so
  a spreadsheet may run them as formulas. The app warns before the export not to
  open the file in a spreadsheet application.
- **Backup mirrors and settings.** A backup mirror folder may be a network path (UNC
  share or mapped drive); device and namespace paths are refused. `settings.json`
  is not authenticated, so malware running as the user can change any setting,
  including the mirror folder.
- **Local UI server.** The desktop UI is served by pywebview's built-in HTTP server
  on `127.0.0.1` at a random port, with no Host-header check and no per-launch
  token on file requests. A DNS-rebinding page could therefore read what that
  server serves: the static UI bundle (`localvault/assets/ui`: `index.html`,
  `popup.html` and their scripts and styles), which holds no vault data. The
  app's own calls go through the WebView2 bridge, not this server.
- **Licence revocations** are fetched only together with an update check. With
  strict offline mode on, a client sees new revocations only when the user runs a
  manual check and accepts the network request.
